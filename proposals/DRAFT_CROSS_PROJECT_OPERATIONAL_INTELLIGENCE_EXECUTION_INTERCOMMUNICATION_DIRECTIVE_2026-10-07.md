# Cross-Project Operational Intelligence and Execution Intercommunication Directive

Status: **DRAFT — PRIMARY REVIEW REQUIRED**  
Origin: user-directed architecture proposal  
Target project: `intercommunicationsenhancements`  
Proposed deployment scope: project architecture / bootstrap / swarm-wide only after Primary review and validation  
Mutation authority conveyed by this artifact: **NO**

## User directive

Conduct a forensic architectural analysis and implementation pass on the Intercommunications system to determine how agents, researchers, managers, projects, and swarms can safely gain operational benefit from work occurring elsewhere in the wider system without incorrectly assuming that separate execution contexts are inherently connected.

The objective is to evolve the architecture from isolated intelligent agents with shared context into a governed system capable of:

- sharing useful discoveries;
- propagating institutional knowledge;
- exposing available expertise;
- routing relevant work;
- coordinating active execution;
- preserving authority and provenance;
- preventing accidental context contamination; and
- allowing one project to benefit from intelligence generated by another even when no dedicated researcher is directly assigned to it.

This must **not** be implemented as uncontrolled global context sharing.

The architecture must explicitly distinguish between:

1. capability;
2. knowledge;
3. execution;
4. authority;
5. availability;
6. provenance;
7. temporal state; and
8. project scope.

These are separate concepts and must never be collapsed into one another.

## 1. Core architectural principle

> Shared intelligence infrastructure is not the same thing as shared execution.

An agent may benefit from knowledge produced elsewhere without possessing the tools, permissions, authority, or active processing resources of the agent that produced it.

Likewise, the existence of researchers or managers elsewhere in the system must not cause an agent to falsely represent that those agents are currently working on its project.

The architecture should therefore support graduated forms of intercommunication rather than binary connected/disconnected behavior.

## 2. Intercommunication layers

### Layer A — Local execution capability

Represents what the current agent or project can actually do now. Track available tools, permissions, connected services, files, APIs, execution environment, compute constraints, project-local instructions, and security boundaries.

Never infer capability merely because another agent possesses it.

### Layer B — Shared institutional knowledge

Represents reusable intelligence generated elsewhere, including research findings, architectural discoveries, validated prompts, governance rules, failure patterns, successful workflows, testing procedures, implementation techniques, system-wide terminology, and forensic conclusions.

Every transferred item should preserve source, originating project, originating agent/role when available, timestamp, confidence, validation state, version, scope, dependencies, and supersession state.

### Layer C — Expertise awareness

The system should be able to know that expertise exists elsewhere without implying availability or assignment. Expertise awareness may support delegation recommendations, reusable-output discovery, duplicate-investigation detection, specialist discovery, and collaboration suggestions.

### Layer D — Active work routing

Actual execution must be deliberately routed between projects or agents through an explicit mechanism. Candidate operations include:

- `REQUEST_RESEARCH`
- `REQUEST_REVIEW`
- `REQUEST_VALIDATION`
- `REQUEST_MANAGER_REVIEW`
- `REQUEST_FORENSIC_ANALYSIS`
- `REQUEST_IMPLEMENTATION`
- `REQUEST_COMPARISON`
- `REQUEST_PEER_REVIEW`

A routed task must preserve requester, originating project, objective, authority, priority, deadline, timezone, dependencies, deliverable, return route, and stop conditions.

### Layer E — Result propagation

Completed work should be capable of returning to the requesting agent, requesting project, shared knowledge repository, relevant managers, dependent tasks, or other explicitly subscribed consumers.

Result propagation must not mean broadcasting everything globally. Use relevance and scope controls.

## 3. Project Intelligence Bus

Evaluate a conceptual **Project Intelligence Bus** or equivalent mechanism that allows projects to expose structured intelligence without sharing their entire private working context.

Candidate message classes:

## 5. Knowledge versus active participation

The system must prevent statements such as "the researchers are working on this" unless researchers are actually executing work against the task.

Explicitly distinguish:

- **Knowledge benefit:** this project can use findings produced by researchers elsewhere.
- **Active participation:** a researcher has been assigned a task and is presently an execution participant.

This distinction must survive agent-to-agent communication and summarization.

## 6. Cross-project discovery

Before starting a substantial investigation, agents should be able to determine whether useful work already exists elsewhere by asking conceptually:

```text
Has another project already researched this?
Is there a validated finding?
Does another agent possess relevant expertise?
Is an investigation currently underway?
Is there an existing artifact that should be reused?
```

The system should favor reuse when appropriate but never blindly trust prior work. Existing findings must retain validation metadata.

## 7. Cross-project delegation

If another researcher, manager, swarm, or specialized project could materially improve a task, the system should support generating a structured delegation request while preserving the full semantic contract: objective, constraints, assumptions, definitions, deadlines, timezone, expected output, evidence requirements, and acceptance criteria.

Do not compress a detailed research contract into an ambiguous shorthand request.

## 8. Manager-level coordination

Managers should gain visibility into relevant distributed work without becoming mandatory bottlenecks. They should be able to understand available/occupied researchers, active investigations, duplicate investigations, blocked work, pending validations, unresolved conflicts, newly generated high-value findings, deadlines, and cross-project dependencies.

Managers may consolidate, reprioritize, delegate, request peer review, cancel accidental duplication, escalate conflicts, and promote findings into shared institutional knowledge.

## 9. Temporal semantics

Time must be a first-class component of cross-project coordination. Relevant directives/tasks should preserve creation time, originating timezone, due time, cadence, recurring schedule, dependencies, expiration, and stop conditions.

Example:

```text
Current time: 05:00 America/Vancouver
Deadline: 08:00 America/Vancouver
Remaining execution window: 3 hours
```

A later handoff must recalculate remaining time from the original temporal anchor rather than reinterpret relative temporal language.

## 10. Authority and directive hierarchy

Cross-project communication must not accidentally elevate lower-level instructions. Maintain the governing hierarchy already established by the Intercommunications architecture. At minimum, preserve:

1. platform / safety / legal constraints;
2. current explicit user directives and temporal directives;
3. project governance;
4. manager directives;
5. agent / research tasks;
6. heuristics and defaults.

A lower layer may not silently override a higher layer. Task transfer must preserve authority metadata.

## 11. User overrides

A current user override must propagate to affected active work without requiring the user to restate every unaffected instruction.

Example:

```text
Original: Research A, B, and C. Complete by 08:00. Validate with two researchers.
Override: Skip B and prioritize C.
Result: Research A and C. Prioritize C. Complete by 08:00. Validate with two researchers.
```

Unaffected constraints survive across project boundaries.

## 12. Conflict handling

When independent agents disagree, do not overwrite one result with another. Preserve a conflict object or equivalent containing both conclusions, supporting evidence, confidence, source, assumptions, and unresolved questions.

Resolution paths may include manager review, additional researcher, forensic review, empirical test, or user decision.

Disagreement is information; preserve it.

## 13. Provenance

No important cross-project finding should become detached from its origin. A receiving agent should be able to determine where information came from, who or what produced it, when, under what directive, whether it was independently validated, and whether it has been superseded.

## 14. Security and information boundaries

Cross-project intelligence must follow least-privilege principles. Do not assume that every project should globally expose every piece of context.

Evaluate classifications such as:

- project-local;
- reusable;
- system-wide;
- restricted;
- sensitive;
- user-only;
- shareable metadata only.

Transfer the minimum information required for the task.

## 15. Context-compression resilience

Determine what information must never be lost during compression. At minimum consider active directives, authority hierarchy, deadlines, unresolved conflicts, assigned work, task ownership, dependencies, validated findings, important provenance, stop conditions, pending user decisions, and supersession chains.

Design a canonical state representation if necessary.

## 16. Project-level operational benefit

Explicitly analyze the triggering case: a project has no researcher directly assigned to it while researchers and managers are active in other projects.

Legitimate benefit categories include:

- **Passive benefit:** access to validated shared findings.
- **Discovery benefit:** ability to locate existing research.
- **Expertise benefit:** knowledge of relevant specialists.
- **Routing benefit:** ability to request help.
- **Managerial benefit:** awareness of system-wide coordination decisions.
- **Learning benefit:** improved procedures derived from work performed elsewhere.
- **Active execution benefit:** only when another agent is explicitly assigned or routed work.

The system must never confuse these categories.

## 18. Event-driven knowledge propagation

Investigate event-driven propagation for high-value changes rather than continuous polling. Examples include architectural vulnerability discovery, directive supersession, validated reusable prompts, research contradictions, and approaching deadlines.

Avoid indiscriminate notifications. Use relevance filtering.

## 19. Cross-project subscriptions

Evaluate category-based subscriptions so projects can consume relevant classes of intelligence without global-context overload.

## 20. Duplicate-work detection

Detect substantial duplicate investigations but do not automatically terminate them. Determine whether duplication is accidental, provides useful independent validation, tests different hypotheses, or should remain isolated for methodological reasons.

## 21. Independent validation

Support both `COLLABORATIVE_MODE` and `INDEPENDENT_VALIDATION_MODE`. In independent mode, prior conclusions may be withheld until the researcher submits its result to reduce contamination and preserve forensic value.

## 25. Bootstrap principle to test

Evaluate, improve, validate, or reject the following candidate principle:

> Agents operate within explicit execution contexts, but may participate in a wider governed intelligence network. Knowledge, expertise, capability, authority, availability, and execution are separate properties. Agents should reuse validated intelligence and discover relevant work across project boundaries where permitted, while never implying active participation, capability, or authority that has not actually been assigned. Active cross-project work requires explicit routing; transferred intelligence must preserve provenance, scope, temporal semantics, directive authority, and validation state.

Do not adopt the wording automatically. Improve it if forensic analysis produces a stronger formulation.

## 26. Primary execution request

Primary is asked to inspect the current Intercommunications architecture, compare this model against what already exists, identify implementation gaps, develop the strongest viable architecture, test it adversarially, and produce concrete bootstrap/system changes.

Reuse existing validated work where appropriate. Preserve independent analysis where validation requires it. Identify delegation opportunities where researchers/managers can materially improve the investigation.

Do not claim that an agent, researcher, manager, or swarm is actively participating unless actual execution has been assigned.

The final objective is a system in which intelligence generated anywhere useful can strengthen work elsewhere **without sacrificing isolation, provenance, security, authority, or truth about who is actually doing the work.**
