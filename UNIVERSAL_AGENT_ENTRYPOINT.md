# Universal Agent Entrypoint

Canonical bootstrap generation: **V26**

This file is the routing rendezvous for launches that are outside every ChatGPT Project or cannot yet prove a host project. It is **not** a shortcut around V26 startup.

## Mandatory V26 pre-bind readiness

Every Intercommunication Enhancements launch begins with the canonical V26 prefix before project binding or task interpretation:

1. Load `PROJECT_MANIFEST_V26.json` and `bootstrap/V26_BOOTSTRAP_ADAPTER.json`.
2. Enter `UNBOUND_READ_ONLY`.
3. Initialize and validate the inherited embedded VMBUS and require `VMBUS_READY`.
4. Load the R10 corrected principal-context layer, R11 model synthesis as revisable non-authoritative hypotheses, and the V26 direct-user chronology as distinct epistemic layers.
5. Build the epistemic/privacy/chronology/synthesis indexes and require `PRINCIPAL_CONTEXT_READY`.
6. Only then resolve and bind an exact project for non-master work.

`PRINCIPAL_CONTEXT_READY` is not identity proof, authentication, authority, consent, or mutation permission. External services are not required for standalone V26 readiness. V25 R11 and earlier generations are preserved historical lineage only.

If a verified host ChatGPT Project exists, perform the same V26 readiness prefix and then execute `protocols/project_context_binding.md`. If no host project can be verified, remain unbound and use this universal routing path.

The universal repository is a routing rendezvous, not automatically the target project:

- machine contract: `GLOBAL_AGENT_ENTRYPOINT.json`
- canonical V26 manifest: `PROJECT_MANIFEST_V26.json`
- canonical V26 adapter: `bootstrap/V26_BOOTSTRAP_ADAPTER.json`
- routing registry: `PROJECT_ROLE_ROUTING_REGISTRY.json`
- project-bound binding policy: `governance/PROJECT_CONTEXT_BINDING_POLICY.json`
- project-bound binding registry: `governance/PROJECT_CONTEXT_BINDING_REGISTRY.json`

## Unbound rule

An unbound agent has no project mutation authority. After V26 standalone readiness it may inspect registered routing metadata and registered read-only coordination/handoff metadata only to resolve exactly one project. Topic similarity, recent chats, repository recency, or a neighboring project's handoff are never sufficient routing authority.

## Existing-project discovery

When no verified host project exists, resolve exactly one project from registered strong evidence such as an explicit project ID, exact registered repository identity/ID, exact registered AgentBus namespace, or exact registered discovery alias. If evidence conflicts, remain unbound for project execution.

After project resolution, bind the project-scoped VMBUS namespace and load the target local `AGENT_BOOTSTRAP.json`, `AGENT_CONTEXT_REFERENCE.md`, identity lock, master handoff, work-control state, and authoritative coordination route before task interpretation or execution.

A verified host project remains strong routing evidence after the V26 readiness barrier; task text, conversation history, repository recency, or another project's state may not silently replace it.

## Role selection

Project binding does not imply PRIMARY. A normal human-launched generic agent without an explicit authorized role enters **roleless demand-driven admission**. Recovery, QA, build, implementation, testing, and review are execution modes/functions, not authority roles.

## Coordination, GitHub, and VMBUS

For Intercommunication Enhancements:

- VMBUS is the standalone runtime/context/readiness layer.
- `/Intercommunication enhancements/AgentBus/messages` is the canonical live project coordination/event stream when that ChatGPT Library surface is available.
- GitHub is the canonical versioned source/governance and durable backup/corroboration layer.
- `INTERNAL_ARTIFACTORY` / `ARTIFACTORY` are legacy compatibility labels for AgentBus in older machine contracts; they do **not** mean JFrog.
- `GITHUB_WRITE != AGENTBUS_WRITE`.
- Whole-store difference is not automatically a record conflict; corresponding records reconcile by logical record ID plus payload SHA-256.

A narrow append-only project-scoped coordination lane never grants protected mutation authority, workflow/release/deployment authority, destructive-operation authority, or cross-project write authority.

## Project separation

Intercommunication Enhancements is the only shared coordination project. Shared protocol/interface compatibility does not share project state, evidence, authority, authorization, or VMBUS namespaces. `PROJECT_A_VMBUS != PROJECT_B_VMBUS`. **CV Support is non-federated and remains separate.**

## New projects and switching

An explicit request to create/seed a new project enters `UNBOUND_PROJECT_SEED`. Create the new project's own identity, coordination namespace, artifact namespace, bootstrap/context material, VMBUS namespace, and handoff; never inherit another project's writable repository or AgentBus state.

A project switch is a deliberate rebind, not a silent routing update. Re-run the V26 readiness boundary as required, discard stale project-specific role/claim context, resolve and verify the new project, then run its local bootstrap.

## Authority

Project discovery and project binding establish scope only. They do not grant protected mutation authority, approval authority, release/deployment authority, workflow authority, security/credential authority, or cross-project write authority. Every protected durable side effect remains subject to the active case-bound authorization policy.
